# RESULTS_SILICON: red-team-on-silicon simulations for the FHSS-Link keyed hop engine

Scope: **simulation only, our own design, no real device and no hardware.** Every result below comes from a Python/numpy model with
*assumed* leakage, fault, trojan and process-variation parameters. None of it measures real silicon; absolute numbers (traces needed,
gate-equivalents, bit-error rates) will differ on a real chip. What transfers is the *shape* of each result (what breaks, what
countermeasure moves which curve, what is not covered). Hop engine under study: `hop = SipHash-2-4(key128, slot_counter64) mod 13`.

Reproduce: `bash run_all.sh` (about 6 minutes, each script under 150 s), `python3 run_tests.py` for the tests, `python3 build_results.py` regenerates this page.

## 1. Power side-channel (CPA) and masking  (`exp1_cpa.py`, `sidechannel.py`, `siphash.py`, figure `figures/fig1_cpa.png`)
Model: per trace 16 samples = Hamming weight of one byte of `v3 = k1^C3^m` (8 samples) and of `v2+v3` (8 samples) plus Gaussian noise of std sigma
(the noise-free HW signal has std 1.41, so sigma=4 is a signal-to-noise power ratio of 0.125). Divide-and-conquer CPA: k1 bytes first, then k0 bytes using the
carry from lower bytes. SipHash-2-4 matches the public reference vectors (n=0..8 and the 15-byte vector from the paper) in `test_siphash.py`.
- Unmasked, 12 trials per point: 90 % full 128-bit key recovery needs about 20 traces at sigma=0.5, 80 at sigma=1, 320 at sigma=2, 640 at sigma=4 (grid is powers of 2, so read as "within a factor 2"). Traces needed scale roughly with sigma squared.
- First-order boolean masking (2 shares, fresh 64-bit mask per run, ISW-based secure adder): the same CPA recovers 4% / 0% / 0% of k1 bytes at 2,000 / 8,000 / 32,000 traces (sigma=1; 3 trials x 8 bytes, chance is 0.4 %). Stage 2 with k1 given as an oracle: 0% at 2,000 traces and 8.3% (2 of 24 bytes) at 8,000; the 32,000-trace stage-2 entry was not run. Per-byte chance is 1/256, so 2 of 24 has p of about 0.004 under pure chance: with only 3 trials this cannot be told apart from a weak residual first-order leak in stage 2 (or luck), so it is not shown to be chance level. Stage 1 (1 of 24 at 2,000 traces) is within chance.
- TVLA-style fixed-vs-random Welch t (20,000 traces per set, max over samples): unmasked 143, masked first order 3.0 (threshold 4.5), masked second order (centred product) 34.
- **Second-order note.** Masking with 2 shares is only first-order secure. A second-order CPA (centred product of the two share samples) recovers all k1 bytes with about 1,000 traces at sigma=0.5, 1,000 at sigma=1 and 8,000 at sigma=2 (all 8 bytes) (fractions in `results/exp1_cpa.json`). So masking raised the cost from tens-to-hundreds of traces to hundreds-to-thousands in this model; it did not make the attack impossible. More shares or a higher-order secure gadget set would be needed against a second-order adversary.
- Controls: with the mask forced to zero the first-order attack recovers 8/8 bytes; if the two shares are held in a register that is overwritten share-by-share (Hamming *distance* between shares = HW of the secret value) it recovers 8/8 bytes at 3,000 traces. Masking is only as good as the physical independence of the share leakage.
- HD variant: the Hamming-distance leakage of the addition hides the most significant bit of every k0 byte; the attack resolves it by lookahead on the carry plus a 256-way check against one hop digest.
- Sequential counter: with a bare slot counter 0..3999 only the 2 low bytes of k1 vary, so only 2 of 8 stage-1 bytes were recovered (the upper bytes have zero input variance). The attack assumes the hash input has varying upper bytes (session nonce / epoch in the message, or a chosen-input adversary).
- Not modelled: glitches and early propagation, internal ISW intermediates, trace misalignment/jitter, real acquisition limits, EM, template attacks, and the attacker's need to know/control the input.

## 2. Fault injection and redundancy  (`exp2_fault.py`, `faultsim.py`, `ge_model.py`, figure `figures/fig2_fault.png`)
Link model: static jammer on 1 of 13 channels, loss probabilities as in `sim/link_sim.py` (0.95 jammed / 0.01 clean). Fault-free PDR of the SipHash engine 0.9200 vs 0.9202 from the existing `link_sim.run` with its LFSR (link_sim has no hook for engine faults, so only the loss model and this fault-free PDR are shared; the fault loop is a new slot-level model). One fault event at slot 0 on the RX side, 1500 trials per cell, 256-slot window. Link recovery: loss of lock after 3 misses, authenticated beacon every 32 slots reloads the counter, watchdog reloads the key from NVM.
- Unprotected (with beacon + watchdog): every counter / key / FSM fault desynchronises the RX. Mean desync duration: counter 28 slots, FSM 28 slots, key 44 slots (37 extra lost packets). Without the watchdog, a key-register upset is never recovered (100% unrecovered in 256 slots, 217 extra lost packets): beacons cannot fix a wrong key.
- TMR on key/counter/FSM/output state (bitwise vote + scrub): single upsets are fully masked (desync 0 in all 4 single-fault classes). Multi-bit upsets spread over three copies sometimes line up on the same bit index: desync 1.9% (2 flips) and 12.9% (4 flips) on the counter, 2.6% on the key (4 flips). This assumes independent random bit positions; adjacent-cell or common-mode upsets would defeat TMR far more often.
- Duplicate + parity + compare (parity per counter word / per key byte, uncorrectable mismatch is detected, key reloaded next slot, counter at next beacon): corrects single-bit upsets in the counter and key words (desync 0 there; the output and FSM single-flip classes are not corrected, see the json: dcp|out|1 desync 1.0, dcp|fsm|1 0.5), but multi-bit and FSM faults are only detected, not corrected (desync 76% for 2 counter flips, 50% FSM). Detection still pays: key faults recover in about 1 slot instead of 45.
- Averaged over the 8 fault classes (equal weight): extra lost packets per fault 25.8 (none), 0.61 (TMR), 4.3 (dup+parity).
- **Cost proxy (gate equivalents, assumed cell areas, not synthesis).** Baseline engine ~6,890 GE. Overhead: TMR on state 53 %, dup+parity+compare 57 %, lockstep duplicate engine (detect only) 100 %, full-engine TMR 200 %. Scaling flop area by 0.7x / 1.3x moves state-TMR by a few percentage points only (`ff_cost_sensitivity_pct` in the json). In this model TMR buys much more than dup+parity for about the same area, because dup+parity cannot correct multi-bit or FSM faults without a tie-break.
- **Differential-fault note (diffusion only).** A single-bit fault in the internal state before round r (0..7) of SipHash-2-4 changes on average 32.0 of 64 output bits for r<=5, 23.4 for r=6 and 7.8 for r=7; 95% of last-round faults give a sparse (<=16-bit) difference, which is the structure differential fault analysis exploits. The hop (value mod 13) changes with probability about 12/13 whatever the round. **I did not implement a DFA key recovery**, did not model how a real fault would be placed (timing, bit control), and did not model faults on TX, in the datapath for the TMR/parity schemes, in voters/comparators/beacon logic, clock or voltage glitching, permanent faults, or adjacent multi-bit upsets.

## 3. Hardware trojan detection  (`exp3_trojan.py`, `trojan.py`, figure `figures/fig3_trojan.png`)
Trojan model: 24-bit slot counter, trigger at a rare count; afterwards, with probability beta = k/256 (select bits tapped from the digest) the channel is replaced ('stuck': fixed channel; 'narrow': h mod 6). Before trigger the output is bit-identical to the clean engine (True over 100,000 hops), so production testing of the hop stream cannot see it. Proxy cost 333 GE (about 4.8 % of the engine).
Detectors see only the channel stream (no key, no target): CUSUM on window chi-square (256-hop windows, tuned for beta=0.03) and a single-window chi-square; both thresholds are set for a 5 % false-alarm probability per 5,000 clean windows (1.28 M hops); measured false-alarm rates 0.050 (CUSUM) and 0.054 (single window).
- 'stuck', CUSUM median delay after the trigger: beta=0.05 3,479 hops (100% detected); beta=0.10 904 hops (100% detected); beta=0.20 343 hops (100% detected); beta=0.40 236 hops (100% detected); beta=0.02 87,571 hops (100% detected); beta=0.012 743,966 hops (61% detected).
- 'narrow' is much harder to see: beta=0.10 10,510 hops (100% detected); beta=0.40 614 hops (100% detected); at beta<=0.03 detection within 2 M hops is partial (see json).
- Delay falls steeply with beta, and the chi-square noncentrality grows with beta squared, but the table does not follow a clean 1/beta^2 law: beta 0.0117 to 0.0195 shortens the delay about 8.5x (2.8x predicted), 0.0195 to 0.0508 about 25x (6.8x predicted), while 0.2 to 0.4 gives only 1.45x (4x predicted; the 256-hop window sets a floor). Also, 'delay' for beta=0.012 is a median over the detected runs only (39 % never detected within 2 M hops), so it is a lower bound for that cell, and '100 % detected' at beta 0.0195 and 0.199 is 299 of 300 runs. Real-SipHash cross-check (12 keys): median CUSUM delay 930 hops at beta=0.10 and 291 at beta=0.20, consistent with the Monte Carlo (which uses ideal uniform hops).
- A golden reference (the receiver regenerates the expected hop from the key) detects after 7 slots at beta=0.10 and 75 at beta=0.012: two to four orders of magnitude faster. It only works when the trojan is in one endpoint and the other is trusted; if both endpoints carry it, only blind statistics remain.
- Existing `sim/randtests.py` on 20,000 post-trigger hops: chi-square p 0.0 for beta=0.02 stuck vs 0.291 clean (a one-shot batch test, not comparable with the online false-alarm budget above).
- Not modelled: trojans that preserve the marginal distribution (e.g. leak key bits through channel choice, correlate hops), analogue/side-channel trojans, a trigger that depends on data rather than a counter, adaptive adversaries who know the detector.

## 4. PUF-derived key  (`exp4_puf.py`, `puf.py`, figure `figures/fig4_puf.png`)
Model: 64 chips x 2048 ring oscillators; frequency = layout plane (gradient spanning 3 sigma) + N(0,1) process variation; read noise 0.05 sigma, independent per-RO temperature coefficient (hot +60 C, cold -40 C); enrolment = majority of 15 reads; 1024 comparison bits per chip.
- Pairing matters (bit-aliasing): comparing far-apart ROs gives uniqueness 24.8% and mean |P(bit)-0.5| of 0.35 (gradient dominates: bad). Removing a per-chip fitted plane first gives uniqueness 49.9%; neighbour pairs give 50.0% (std 0.015). Bit aliasing for the good schemes: mean |p-0.5| = 0.050, max 0.20 (with only 64 chips about 0.05 is the sampling floor).
- Reliability (neighbour pairs): 98.3 % nominal, 95.1 % hot, 96.3 % cold (bit error rate 1.7% / 4.9% / 3.7%; nominal theory arctan(sn/sp)/pi = 1.6%, the rest is enrolment noise).
- Code-offset fuzzy extractor, 128-bit key = SHA-256(secret)[:16]; key-regeneration failure (nominal / hot / cold): no ECC 86% / 100% / 99%; 5-fold repetition 1.5% / 13.4% / 7.2%; BCH(15,7,t=2) x19 3.0% / 47.3% / 24.8%; repetition-3 + BCH 0.00% / 0.23% / 0.00% (1,280 trials per cell, but these are 64 chips x 20 reads, so only 64 enrolments are independent; 0 failures in 1,280 trials is an upper bound of about 2.3e-3 by the rule of three on the reads, and the chip-level bound is looser, so 0.00 % means 'none observed', not 'below 1e-3'). The concatenated code uses 855 of the 1,024 response bits and leaves a failure rate that is still not acceptable for a link that must always boot (0.2 % at +60 C here).
- End to end: the regenerated key reproduced the hop schedule for 960/960 chip-condition trials, and the 64 chips gave 64 distinct keys.
- Honest caveats: the secret comes from an assumed on-chip TRNG; helper data is public and leaks 722 of 855 bits of redundancy by construction (safe only if response bits are close to independent and unbiased, which the entropy numbers here only bound from above, not prove); no helper-data manipulation, aging, voltage, modelling-attack or side-channel analysis of the PUF itself; a pure-Gaussian plane+noise model is much cleaner than real silicon.

## 6. What this does not show
No real device was measured, so none of the leakage, fault or process parameters are validated. The attacks here are textbook-level against a model we wrote ourselves; they say where our design would need attention (mask order, redundancy of the key register, post-trigger statistical monitoring, ECC strength), not that it is secure or insecure in silicon.
